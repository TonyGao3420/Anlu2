## 4. 遇到的困难

### 困难 1（已解决）：工程初期信息缺失

最初只有 `led_blink` 例程，摄像头型号、I2C 地址、寄存器表、引脚全部未知。
**解决**：用户补充 `SC520CS摄像头资料/` 后，解出官方三个 Lab 工程，
逐项确证了上表全部参数，并把官方文件移植进工程。此困难已完全消除。

### 困难 2（已解决）：ModelSim 控制台中文乱码

ModelSim 10.3c 控制台对 UTF-8 中文显示为乱码（且曾把部分本地化字符串置换为 `?`）。
**解决**：改为把仿真输出重定向到文件，再用 `-Encoding UTF8` 读回，
即可正常显示中文与结果。所有验证均采用此法。

### 困难 3（已解决）：`td_commands_prompt.exe` 参数路径被吞

首次调用时，反斜杠路径被 TD 解析成 `D:AnlogicTD_6.2.1...`（去掉所有反斜杠），
报 `couldn't read file ...`。
**解决**：改用正斜杠路径 `D:/Anlogic/TD_6.2.1_Engineer_6.2.168.116/doc/scripts/DefaultFlow.tcl`。

### 困难 4（已解决）：TD 的 XML 工程文件不接受注释

在 `Anlu2.prj` / `Anlu2.al` 里加了 `<!-- -->` 注释后，TD 报
`PRJ-8441 ERROR: Source file format error: XML tag <xmlcomment> is invalid.`
**解决**：两个工程 XML 文件一律去掉注释；说明文档改写进 `doc/`。

### 困难 5（已解决）：`.sv` 包装的 SystemVerilog 非压缩数组端口

`mipi_dphy_rx_ph1p_mipiio_wrapper.sv` 把非压缩数组
（`wire [7:0] S_byte_aligne_data [LANE_NUM-1:0]`）直接接到加密模块的数组端口上，
TD 报 `HDL-8007 ERROR: cannot access memory 'S_byte_aligne_data' directly`。
**尝试过并已排除的方案**：改文件扩展名、调整分析顺序、改用绝对路径、
移除 `.enc.sv`、按依赖重排 `CompileOrder` —— 均无效。
**当前状态**：见困难 6，这是本阶段**唯一的遗留阻塞点**。

### 困难 6（**未解决，本阶段主要阻塞**）：TD `open_project` 分析器拒绝该包装

为定位问题做了 8 组对照实验，结论如下（详见 `doc/architecture.md` 第 8.4 节）：

| 实验 | 方式 | 结果 |

| B | **同一批文件**改用 `open_project` 加载最小 `.prj` | ❌ HDL-8007 |
| C | `.enc.sv` 排到包装之前 | ❌ 同样报错 |
| D | 工程文件用绝对路径 | ❌ 同样报错 |
| E | 工程里不放 `.enc.sv` | ❌ 同样报错 |
| F | 只用自研普通模块 `analyze` + `elaborate` | ✅ 通过 |

**决定性证据（用户补充官方 32 例程后取得）**：

| 证据 | 内容 |
|---|---|
| 官方 `run.log` 头部 | **`Tang Dynasty, V6.1.155545`** —— 官方成功产物出自 **TD 6.1.2** |

| 同一 `.sv` 哈希 | 官方 32 例程与 lab_ex1/lab_ex2 的该文件 **MD5 完全一致**（`A1CB5B2B…`） |

→ 结论：**该官方 SystemVerilog 包装在 TD 6.2.168116 下无法通过 `open_project` 分析**，
与文件内容 / 分析顺序 / 路径均无关。

**解决方案（不更换 TD 版本）**：

关键观察 —— 出问题的只是**中间那层**包装（用了数组端口）；而

- **内层加密模块（`byte_aligner` / `channel_aligner`）的端口都是普通向量**；
- 官方 `ph1p_mipiio_rx_wrapper.v`（物理层硬核包装）**完全不涉及 aligner**。

因此新增 `src/vendor/mipi_dphy_rx_ph1p_wrapper_v2001.v`：
**直接例化内层加密模块**（每 Lane 一个 `byte_aligner` + 一个 `channel_aligner`，
用 `generate` 循环 + 普通向量互连），**不改动任何加密 IP**，
得到功能等价、但全部端口与连线都是普通向量的**纯 Verilog-2001** 包装。

**验证结果（A/B 对照，同一最小工程）**：

|---|---|
| 官方 `.sv` 包装 | ❌ 3 处 HDL-8007 + PRJ-8644 |
| 本工程 v2001 包装 | ✅ **0 error，分析通过** |

**上板前需补齐这些引脚或去掉对应端口。**

### 困难 7：片上存储不足以做整帧缓存

PH1P35MDG324 只有 **108 片 ERAM(20kbit) ≈ 2.1Mbit**，而一帧 1280×720 RGB888
需要 **22.1Mbit**（即使 RGB565 也要 14.7Mbit）。
**结论**：整帧缓存**必须走 DDR**，官方例程用 DDR2 正是这个原因。
本阶段未引入 DDR，因此摄像头 RAW 数据尚无法整帧缓存后上屏。

### 困难 8（已缓解）：官方例程自身时序未收敛

官方 `gate.qor` 显示 `MIPI_RX_BYTE_CLK` 域 Setup WNS = **−2121ps**（两条路径违例）。
本工程沿用同一硬核与速率，原以为会继承该问题；但**本工程实测 opt_gate 阶段
Setup WNS = +8054ps、无违例**（见困难 6 的时序数据），该风险已显著缓解。
仍需以最终 phy（布局布线）流程结果为准。

## 6. 阻塞点解决方案（已完成）

### 6.1 结论

MIPI 包装问题**已在不更换 TD 版本的前提下解决**：

- 新增 `src/vendor/mipi_dphy_rx_ph1p_wrapper_v2001.v`（纯 Verilog-2001），
  **直接例化内层加密模块** `byte_aligner` / `channel_aligner`（它们端口都是普通向量），
  用 `generate` 循环 + 普通向量互连，**不改动任何加密 IP**；
- `src/system_top.v` 与 `Anlu2.prj` / `Anlu2.al` 已切换到该包装；
- 两个数组端口 wrapper（`byte_aligner_wrapper.enc.sv` /
  `channel_aligner_wrapper.enc.sv`）已从工程中移除（v2001 包装不再需要它们）。

**验证**：A/B 对照下官方 `.sv` 报 3 处 HDL-8007，本工程 v2001 包装 **0 error**；
完整综合 `elaborate system_top → optimize_rtl → optimize_gate` 全部通过，

## 7. 结论

1. **工程骨架已建成**：`src/` 30 个源文件、`sim/` 10 个仿真文件、`constrs/` 2 个约束、
   `doc/` 3 份文档（含本报告与 `参考代码/`），目录结构符合 `README.md` 的约定
   （`src/`、`sim/`、`constrs/`、`doc/`），关键逻辑均有中文注释。
2. **视频输出通路已验证**：720p60 时序在 ModelSim 中逐项核对 VESA 参数**全部通过**
   （每帧 1650×750、有效像素 1280×720、user=1、last=720、行/场同步脉宽全部匹配）。
3. **采集通路所需资料已齐备**：SC520CS 的 I2C 地址、芯片 ID、165 条寄存器表、
   AE/AG 表、增益表、真实引脚、时钟树均已确证并落地为代码。
4. **原阻塞点已解决**：MIPI 包装改用纯 Verilog-2001 版本（直接例化内层加密模块，
   绕开 SystemVerilog 数组端口），**在不更换 TD 版本的前提下**通过了完整综合：
   `elaborate system_top → optimize_rtl → optimize_gate` 零错误，
   Setup WNS = **+8054ps**（无违例），Hold WNS = **+431ps**（无违例）。
5. **未完成项已如实列出**，不含任何"看起来完成"的虚报。上板前还需补齐 LED/串口
   引脚约束、并确认 MIPI Lane 顺序。
