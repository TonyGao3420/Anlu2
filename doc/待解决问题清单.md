## 问题 1　`tb_csi2_rx_unpack` 字节馈送时序未对齐，测试未通过

### 位置
- **测试平台**：`sim/tb/tb_csi2_rx_unpack.v`
- **被测 RTL**：`src/camera/csi2_rx_unpack.v`
  - 字节采集：`r_lane_idx` 逻辑（约第 65–130 行）
  - 输出队列：`r_pq0..r_pq3` / `r_pq_cnt`（约第 145–175 行）
  - RAW10 解包：`w_raw10_0..3` 与 `P_PAYLOAD` 分支

### 现象
```
bytes sent  = 44
pixels      = 0 (expected 16)
frame_start = 1 (expected 1)     ← 已正确
frame_end   = 0 (expected 1)
errors      = 0
TEST FAILED: tb_csi2_rx_unpack
```

用 trace 实测到的关键事实：

1. **`csi2_rx_unpack` 一拍消耗 `CSI_LANES` 个字节**
   （`I_hs_data` 中 lane0 在最低 8 位、lane1 在次低 8 位）；
2. `r_hdr` 的字节落位**比预期差 2 个字节**
   （期望 `0x2B000000`，实测 `0x00002B00`）→ 字节流被多消耗约 2 拍；
3. `r_pack_cnt` 恒为 0，状态机**从未进入 `P_PAYLOAD`**。

### 解决方案
**已在 RTL 侧修复的 3 个真实 bug**（编译/运行已验证，`frame_start` 由 3 修正为 1 即为证据）：

| # | Bug | 修复 |
|---|---|---|
| 1 | RAW10 每 5 字节只输出 1 个像素 | 改为一次解出 4 个像素写入 4 级输出队列，再由队列连续 4 拍送出；RAW12 同理 |
| 2 | 单 Lane 时 `I_hs_data[15:8]` 位选越界（仿真加载即崩 `vsim-3374`） | 改用 **`generate` 条件生成**（普通 `if` 无效：ModelSim 细化期会求值所有分支） |
| 3 | 短包只跳过 1 个字节，ECC 被当新包头 → 反复产生 `frame_start` | 改为等**两个 ECC 字节都收完**才触发帧边界 |

**剩余待修（测试平台侧）**，按优先级：
1. ~~把 `flush_txbuf` 改为**两段式驱动**~~ —— **本轮已尝试，无效**
   （已实现"先在 `hs_valid=0` 时建立 `hs_data`，下一拍再拉 `hs_valid`"，
   结果不变：`frame_start=1`、`pixels=0`）。说明**不是驱动竞争**问题，
   而是模块内部的字节消耗节奏与 TB 的预期不一致。
2. **下一步应直接核对 RTL 的字节消耗节奏**（重点怀疑对象）：
   `r_lane_idx` 的推进与 `r_byte_vld` 的产生关系 ——
   trace 实测 `r_hdr` 偏移 2 字节、且 `r_pack_cnt` 恒为 0（从未进 `P_PAYLOAD`），
   高度怀疑 `r_lane_idx` 在 `hs_valid` 连续为高时会**跨包继续累加**，
   而 TB 是按"每个 word 独立一拍"馈送的，两者节拍必然错开。
   → 建议在 TB 里**在包与包之间插入 1 拍 `hs_valid=0` 的空闲**，
   让模块的 lane 计数在每个包开始时复位到 lane0。
3. 备选：在 RTL 侧增加"每个包开始时重置 `r_lane_idx`"的显式同步点
   （这是合理的 RTL 改进，可让模块不依赖外部严格的节拍）。


### 是否需要外部信息
❌ **不需要**。纯测试平台/自研 RTL 改动，ModelSim 可独立验证。

## 问题 2　`tb_sc520_cfg` 从机模型未对齐 `uii2c` 的 SCL 相位

### 位置
- **测试平台**：`sim/tb/tb_sc520_cfg.v`（从机模型在 `always @(posedge clk)` 块内）
- **被测 RTL**：`src/camera/config/sc520_cfg.v`（`uicfgcs520`，官方代码）
- **协议实现**：`src/vendor/uii2c.v`（米联客 I2C 主机）

### 现象
```
ERROR: 无从机时未在预期时间内置起 iic_error
ERROR: slave got wrong device addr 0x93      ← 正确应为 0x6C
sensor_id=0xZZZZ id_ok=0 cfg_done=0 iic_err=0 wr=0
TEST FAILED: tb_sc520_cfg
```
从机**确实在通信**（收到了字节），但字节值错。

### 解决方案
**根因已定位**：`uii2c` 的 SCL 相位特殊 ——
```verilog
assign scl_offset = (clkdiv == OFFSET);      // OFFSET = SCL_DIV - SCL_DIV/4
always @(posedge I_clk) O_iic_scl <= scl_offset ? scl_r : O_iic_scl;
```
`O_iic_scl` 相对内部 `scl_clk` 有 **3/4 个半周期的延迟偏移**，
而 SDA 在 `scl_clk` 边沿变化。普通"检测 SCL 上升沿当拍采样"会采到跳变值。

**修法**（纯测试平台改动）：
1. 从机改为**在 SCL 高电平中点采样**（而非上升沿当拍）；
2. 或对 SCL 做 4 倍过采样 + 数字滤波后在稳定区采样；
3. 同时按 `CLK_DIV=36` 重算"无从机时 `iic_error` 的预期时间"（当前等待窗口可能偏小）。

**已完成的准备工作**：测试平台已从"4 状态机"重写为**标准 I2C 事务模型**
（第 1 字节判 R/W；写事务收地址+数据；读事务回 0xEE/0x4B），
并区分**负向用例**（无从机 → 应报错误且不挂死）与**正向用例**（有从机 → ID 通过 + 写寄存器）。

### 是否需要外部信息
❌ **不需要**。`uicfgcs520` / `uii2c` 是官方代码，问题只在自研测试平台。

## 问题 4　摄像头 RAW 通路未接入 HDMI 输出

### 位置
- **顶层**：`src/system_top.v`
  - 第 **215–241** 行 `csi2_rx_unpack` 实例（`w_pix_valid` / `w_pix_data` 已解出但未被使用）
  - 第 **253–262** 行 图案选择：`w_pattern_sel` 恒为 `PATTERN_SEL_DEFAULT`
  - 第 **25** 行注释：`+--> (留待接入 demosaic/RAW->RGB)`

### 现象
HDMI 输出的是**内置测试图案**（彩条/渐变/棋盘），摄像头数据没有上屏。

### 缺失的两个环节
1. **Bayer→RGB 去马赛克**（RAW10 → RGB888）；
2. **跨时钟域帧缓存**：MIPI 字节时钟域（`w_csi_rx_clk`，约 103.5MHz）
   → HDMI 像素时钟域（`w_clk_pixel`，75MHz）。

### 解决方案
**必须先决策帧缓存方案**（这是本问题的关键约束）：

一帧 1280×720 RGB888 需 **22.1 Mbit**，而片上 ERAM 仅 **108 片 ≈ 2.1 Mbit**，
差一个数量级，因此必须三选一：

| 选项 | 说明 | 代价 |
|---|---|---|
| A1 引入 DDR2 帧缓存 | 与官方例程一致，可整帧 720p 实时显示 | 需引入官方 `ph1p35_ddr/ddr2` 全套（100+ 文件）+ DDR IP；DDR 校准失败会黑屏，排查成本高 |
| A2 不用 DDR，行缓存流式处理 | 纯 RTL、纯 BRAM，全程可仿真、时序风险低 | **无法整帧缓存** → 输出需降到 640×480，或做 2×2 降采样 |
| A3 先做 A2 打底，DDR 作为可插拔后端 | 先把"采集+输出"主线跑通并验证，DDR 后置 | 需先定义帧缓存接口抽象 |

**建议 A3**。方案确定后的实现步骤：
1. 新增 `src/isp/bayer2rgb.v`（3×3 双线性去马赛克，参考
   `doc/参考代码/sc500官方ISP/raw8_2_rgb888.v` + `Line_Shift_RAM_8Bit.v`）；
2. 新增跨时钟域帧缓存（`frame_buffer`，写域 `w_csi_rx_clk`、读域 `w_clk_pixel`）；
3. 在 `system_top` 中把 `w_pattern_sel` 的源改为"摄像头数据 / 测试图案"二选一。

### 是否需要外部信息
✅ **需要** —— 但需要的是**决策**，不是资料：**请从 A1/A2/A3 中选定一个帧缓存方案**。
除该决策外，其余实现均可自行完成。

## 问题 5　MIPI Lane 顺序未经上板确认

### 位置
`src/vendor/mipi_dphy_rx_ph1p_wrapper_v2001.v`，两处可一键交换的地方：
1. `G_LANE_ALIGN` 生成块内，`byte_aligner` 的输入位选：
   `.I_hs_data (S_hs_rx_data[LANE_W*i +: LANE_W])`
2. `G_DATA_MERGE` 生成块内，输出位选：
   `assign O_hs_rx_data[LANE_W*j +: LANE_W] = S_ch_aligner_data[LANE_W*j +: LANE_W];`

### 现象
无法静态判定 Lane 映射是否正确：
- 官方 `.sv` 包装用**索引反向**
  （`O_hs_rx_data[8*(i+1)-1:8*i] = S_ch_aligner_data[LANE_NUM-1-i]`）；
- 本工程 v2001 包装用**顺序映射**；
- 但决定切分方式的 `byte_aligner_wrapper.enc.sv` 是**加密文件，内部不可读**。

若映射反了，图像会出现通道错位（左右/颜色错）。

### 解决方案
**上板实测**：用彩条或已知图案确认；若错位，交换上述两处位选即可，
**不需要重新设计**。代码中已标注这两处位置。

### 是否需要外部信息
✅ **需要外部支持（物理硬件）** —— 需开发板 + SC520CS 摄像头 + HDMI 显示器。
这是**唯一无法靠软件完成**的验证项。
